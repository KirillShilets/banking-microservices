### A6. Пиннинг actions по SHA — не вручную, а инструментом

Гадать SHA бессмысленно и опасно (можно закрепить не ту версию). Добавьте шаг пиннинга как часть процесса, а не как захардкоженный список:

`deploy/ci/pin-actions.sh`:

```bash
#!/usr/bin/env bash
# Pins every `uses: owner/repo@vX` in .github/workflows to its commit SHA,
# keeping the version as a trailing comment so Dependabot can still bump it.
# Requires: https://github.com/stacklok/frizbee (or `gh` CLI as fallback below).
set -euo pipefail
cd "$(dirname "${BASH_SOURCE[0]}")/../.."

if command -v frizbee >/dev/null 2>&1; then
  frizbee actions .github/workflows --quiet
  exit 0
fi

echo "frizbee not found; falling back to manual gh-cli resolution" >&2
for f in .github/workflows/*.yml; do
  grep -oE 'uses: [^@]+@v[0-9][^ ]*' "$f" | sort -u | while read -r line; do
    ref="${line#uses: }"
    repo="${ref%@*}"; tag="${ref#*@}"
    sha="$(gh api "repos/$repo/commits/$tag" --jq .sha 2>/dev/null || true)"
    [ -n "$sha" ] || { echo "WARN: could not resolve $ref" >&2; continue; }
    sed -i "s#uses: ${repo}@${tag}#uses: ${repo}@${sha} # ${tag}#g" "$f"
  done
done
```

Запуск: `bash deploy/ci/pin-actions.sh`, затем `git diff` — проверить, что версии не «уехали» (frizbee/gh резолвит тег в SHA **на момент запуска**, пересчитывайте при каждом обновлении). После пиннинга Dependabot (`package-ecosystem: github-actions`, уже заведён в этапе 5.4) сам будет открывать PR на обновление SHA с актуальным комментарием версии — это штатное поведение, ничего дополнительно настраивать не нужно.

Сделайте этот скрипт частью чек-листа: **запускать перед каждым релизом цепочки `release.yml`**, пока не добавите политику, требующую пиннинга (можно добавить `actionlint`-плагин или grep-проверку в `ci.yml`):

```yaml
  # добавить job в ci.yml
  actions-pinned:
    name: Actions must be pinned by SHA
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4   # сам этот checkout тоже запиньте после первого прогона pin-actions.sh
      - run: |
          if grep -rE 'uses: [^@]+@v[0-9]' .github/workflows/ | grep -v '#'; then
            echo "Found workflow steps not pinned by commit SHA"; exit 1
          fi
```

Добавьте `actions-pinned` в `needs` джобы `ci-success`.

### A7. Trivy до push + деплой по digest (вместо мутабельного тега)

Это самый важный патч — переписываю job `images` в `release.yml` целиком на схему «push sha-дайджест с аттестациями → скан по digest → только при успехе создать semver-тег на тот же digest → подписать digest»:

```yaml
  images:
    name: Image ${{ matrix.name }}
    runs-on: ubuntu-latest
    timeout-minutes: 30
    permissions:
      contents: read
      packages: write
      id-token: write
    outputs:
      account-service: ${{ steps.collect.outputs.account-service }}
      bill-service: ${{ steps.collect.outputs.bill-service }}
      deposit-service: ${{ steps.collect.outputs.deposit-service }}
      notification-service: ${{ steps.collect.outputs.notification-service }}
      gateway-service: ${{ steps.collect.outputs.gateway-service }}
      frontend: ${{ steps.collect.outputs.frontend }}
    strategy:
      fail-fast: false
      matrix:
        include:
          - { name: account-service,      context: ".",       file: account-service/Dockerfile }
          - { name: bill-service,         context: ".",       file: bill-service/Dockerfile }
          - { name: deposit-service,      context: ".",       file: deposit-service/Dockerfile }
          - { name: notification-service, context: ".",       file: notification-service/Dockerfile }
          - { name: gateway-service,      context: ".",       file: gateway-service/Dockerfile }
          - { name: frontend,             context: frontend,  file: frontend/Dockerfile }
    steps:
      - uses: actions/checkout@v4
      - run: echo "OWNER=$(echo "$GITHUB_REPOSITORY_OWNER" | tr '[:upper:]' '[:lower:]')" >> "$GITHUB_ENV"
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      # Шаг 1: публикуем ТОЛЬКО по sha-тегу (неизменяемому), с provenance/SBOM.
      # Семантический тег пока не существует — его некому использовать до скана.
      - id: build
        uses: docker/build-push-action@v6
        with:
          context: ${{ matrix.context }}
          file: ${{ matrix.file }}
          push: true
          tags: ghcr.io/${{ env.OWNER }}/bank-${{ matrix.name }}:sha-${{ github.sha }}
          cache-from: type=gha,scope=${{ matrix.name }}
          cache-to: type=gha,mode=max,scope=${{ matrix.name }}
          provenance: true
          sbom: true

      # Шаг 2: сканируем именно опубликованный digest, а не локальный tar.
      - name: Scan image by digest
        uses: aquasecurity/trivy-action@0.28.0
        env:
          TRIVY_USERNAME: ${{ github.actor }}
          TRIVY_PASSWORD: ${{ secrets.GITHUB_TOKEN }}
        with:
          image-ref: ghcr.io/${{ env.OWNER }}/bank-${{ matrix.name }}@${{ steps.build.outputs.digest }}
          severity: 'HIGH,CRITICAL'
          ignore-unfixed: true
          exit-code: '1'

      # Шаг 3: только если скан прошёл — присваиваем семантический тег
      # тому же digest. Rebuild не нужен, манифест не меняется.
      - name: Promote digest to release tag
        run: |
          VERSION="${GITHUB_REF_NAME#v}"
          docker buildx imagetools create \
            --tag "ghcr.io/${{ env.OWNER }}/bank-${{ matrix.name }}:${VERSION}" \
            "ghcr.io/${{ env.OWNER }}/bank-${{ matrix.name }}@${{ steps.build.outputs.digest }}"

      - uses: sigstore/cosign-installer@v3
      - name: Sign image by digest
        run: cosign sign --yes "ghcr.io/${{ env.OWNER }}/bank-${{ matrix.name }}@${{ steps.build.outputs.digest }}"

      - id: collect
        run: echo "${{ matrix.name }}=${{ steps.build.outputs.digest }}" >> "$GITHUB_OUTPUT"
```

Что это даёт:
- Под мутабельным семантическим тегом **никогда** не может оказаться образ, не прошедший Trivy — его физически не существует до строки `imagetools create`.
- `cosign sign` подписывает **digest**, а не тег — значит подпись валидна для обоих тегов (`sha-...` и `X.Y.Z`) одновременно, подмена тега её не обходит.
- Появился `outputs.<service>` с digest'ом — это нужно для пункта «деплой по digest» (ниже, A8) и для `promote.yml`.

`job chart` оставляем как есть, он не меняется.

### C4. Prod: pinned revision, а не плавающий `main`

Ручной Sync на `targetRevision: main` опасен — можно случайно выкатить не тот коммит. Prod должен следить за **тегом**, который проставляет сам `promote.yml` после смены `values-prod.yaml`.

```yaml
# deploy/argocd/app-prod.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: bank-prod
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: bank
  source:
    repoURL: https://github.com/OWNER/spring-cloud-banking-system.git
    targetRevision: promote/prod   # ветка, а не main — см. ниже
    path: helm/bank-platform
    helm:
      releaseName: bank
      valueFiles:
        - values-managed.yaml
        - values-prod.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: bank-prod
  syncPolicy:
    syncOptions:
      - CreateNamespace=true
    retry:
      limit: 3
      backoff: { duration: 30s, factor: 2, maxDuration: 5m }
  # automated отсутствует — Sync только руками
```

Для этого `promote.yml` для prod не должен удалять ветку `promote/prod` после merge — измените `peter-evans/create-pull-request` для prod-кейса: `delete-branch: false`, и **не сквош-мёржить** PR в `main`, а мёржить обычным merge commit в саму ветку `promote/prod`, либо проще — держать `promote/prod` как долгоживущую ветку, в которую мёржится `main` + изменённый `values-prod.yaml`. Это усложнение, но так ручной Sync в Argo CD никогда не подхватит незапланированный коммит из `main`.

Более простой и равноценный вариант, если не хотите возиться с долгоживущей веткой: оставить `targetRevision: main`, но добавить в `app-prod.yaml` аннотацию с ожидаемым тегом и сверять её вручную перед Sync — компромисс хуже, но проще. **Рекомендую первый вариант** (отдельная ветка) для банковского домена.

## Блок D. Переcцепление `promote.yml` на реальное завершение `release.yml`

### D1. Делаем `release.yml` вызываемым и добавляем финальный job

### D2. `promote.yml` триггерится по завершению `release.yml`, не по `release: published`

```yaml
name: promote

on:
  workflow_run:
    workflows: [Release]
    types: [completed]
  workflow_dispatch:
    inputs:
      version:
        description: Version without v prefix, for example 1.2.3
        required: true
      environment:
        description: Target environment
        type: choice
        options: [staging, prod]
        default: staging

permissions:
  contents: write
  pull-requests: write
  packages: read

jobs:
  bump:
    if: >
      github.event_name == 'workflow_dispatch' ||
      (github.event.workflow_run.conclusion == 'success' &&
       startsWith(github.event.workflow_run.head_branch, 'refs/tags/v') == false &&
       github.event.workflow_run.event == 'push')
    runs-on: ubuntu-latest
    environment: ${{ (inputs.environment || 'staging') == 'prod' && 'production' || 'staging' }}
    env:
      ENVIRONMENT: ${{ inputs.environment || 'staging' }}
```

Здесь ключевая проблема: `workflow_run.head_branch` для тег-триггера содержит **имя тега**, а не `refs/tags/...` — GitHub отдаёт его без префикса. Поэтому условие выше нужно упростить и опираться на сам тег:

```yaml
jobs:
  bump:
    if: github.event_name == 'workflow_dispatch' || github.event.workflow_run.conclusion == 'success'
    runs-on: ubuntu-latest
    environment: ${{ (inputs.environment || 'staging') == 'prod' && 'production' || 'staging' }}
    env:
      ENVIRONMENT: ${{ inputs.environment || 'staging' }}
      RAW_VERSION: ${{ inputs.version || github.event.workflow_run.head_branch }}
```

`head_branch` при срабатывании `workflow_run` на push тега **равен имени тега** (например `v1.2.3`), это задокументированное поведение GitHub. Дальше код `promote.yml` не меняется — `RAW_VERSION` по-прежнему содержит `v1.2.3`, и `${RAW_VERSION#v}` отработает как раньше.

Это устраняет сразу обе проблемы из вашего пункта 2: промоушен больше не стартует параллельно со сборкой (он ждёт `completed`), и красный `release.yml` не запускает дальнейшую цепочку, потому что `conclusion == 'success'` отфильтровывает падения.

### D3. Digest вместо тега в `promote.yml`

Раз в блоке A7 `release.yml` теперь даёт надёжный semver-тег только после успешного скана, `promote.yml` может продолжать ставить `tag`, это безопасно. Но для максимальной защищённости (и чтобы использовать задел из A8) замените шаг ожидания образов на получение digest и запись его в `values-<env>.yaml`:

```yaml
      - name: Resolve digests and bump
        run: |
          OWNER=$(echo "$GITHUB_REPOSITORY_OWNER" | tr '[:upper:]' '[:lower:]')
          VERSION="${RAW_VERSION#v}"
          f="helm/bank-platform/values-${ENVIRONMENT}.yaml"
          for s in account-service bill-service deposit-service notification-service gateway-service frontend; do
            for i in $(seq 1 60); do
              digest="$(docker buildx imagetools inspect "ghcr.io/${OWNER}/bank-${s}:${VERSION}" --format '{{json .Manifest.Digest}}' 2>/dev/null | tr -d '"' || true)"
              [ -n "$digest" ] && break
              [ "$i" = 60 ] && { echo "missing ${s}:${VERSION}"; exit 1; }
              sleep 30
            done
            yq -i ".services[\"$s\"].image.tag = \"$VERSION\"" "$f"
            yq -i ".services[\"$s\"].image.digest = \"$digest\"" "$f"
          done
          echo "VERSION=$VERSION" >> "$GITHUB_ENV"
```

Это требует, чтобы хелпер из A8 (`bank-platform.image`) уже был в чарте — иначе поле `digest` просто будет лежать неиспользуемым, без вреда, но и без пользы.

## Блок E. Миграции Liquibase отдельным Job-хуком

### E1. Отключаем автозапуск миграций в рантайме

В `application.yml` (или `application-kubernetes.yml`, смотрите, как у вас разложена конфигурация — **ПРОВЕРЬТЕ**, какой профиль реально активен в поде) каждого сервиса с БД добавьте:


Без этого при `replicas: 3` все три пода одновременно попытаются взять Liquibase changelog lock — в лучшем случае будет гонка с задержками (`liquibase lock already held`), в худшем — битая блокировка при убитом поде посреди миграции.

### E2. Helm-хук `pre-upgrade, pre-install`

Создайте `helm/bank-platform/templates/migration-job.yaml`. Шаблон делает по одному Job на каждый `-service`, у которого объявлена БД (ориентируюсь на структуру `services.<name>.image` из values — **ПРОВЕРЬТЕ** реальные имена ключей env/secret в вашем `deployment.yaml` и скопируйте их сюда один в один, ниже только каркас):

```yaml
{{- range $name, $svc := .Values.services }}
{{- if and $svc.enabled $svc.database }}

kind: Job
metadata:
  name: {{ printf "%s-%s-migrate" (include "bank-platform.fullname" $) $name }}
  namespace: {{ $.Release.Namespace }}
  annotations:
    "helm.sh/hook": pre-upgrade,pre-install
    "helm.sh/hook-weight": "-5"
    "helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded
  labels:
    app.kubernetes.io/name: {{ $name }}
    app.kubernetes.io/component: migration
spec:
  backoffLimit: 2
  template:
    metadata:
      labels:
        app.kubernetes.io/name: {{ $name }}
        app.kubernetes.io/component: migration
    spec:
      restartPolicy: Never
      {{- with $.Values.global.imagePullSecrets }}
      imagePullSecrets:
        {{- toYaml . | nindent 8 }}
      {{- end }}
      securityContext:
        runAsNonRoot: true
        seccompProfile: { type: RuntimeDefault }
      containers:
        - name: migrate
          image: {{ include "bank-platform.image" $svc.image }}
          args: ["--spring.liquibase.enabled=true", "--spring.main.web-application-type=none"]
          # ПРОВЕРЬТЕ: если у сервиса нет отдельного режима "только миграция",
          # замените args на профиль, который поднимает контекст и сразу завершает
          # процесс после ChangelogExecutor, либо используйте отдельный
          # liquibase/liquibase-образ с changelog, смонтированным из ConfigMap.
          envFrom:
            {{- toYaml $svc.envFrom | nindent 12 }}
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: ["ALL"] }
          resources:
            requests: { cpu: 100m, memory: 256Mi }
            limits: { cpu: 500m, memory: 512Mi }
{{- end }}
{{- end }}
```

**Это самое слабое место патча**, и я явно это помечаю: запуск Spring Boot приложения с `web-application-type=none` только ради миграции — рабочий, но тяжёлый паттерн (поднимается весь контекст). Более чистый вариант — вынести Liquibase changelog в отдельный slim-образ (`liquibase/liquibase` + changelog как ConfigMap/volume) и гонять `liquibase update` без Spring вообще. Это требует знания, как у вас разложены changelog-файлы (classpath vs внешний каталог), чего я не видел. **ПРОВЕРЬТЕ структуру `src/main/resources/db/changelog` в каждом сервисе** перед тем, как решать, какой вариант брать — если changelog простой (один файл на сервис), выгоднее отдельный liquibase-образ.

## Блок F. Pod Security, NetworkPolicy, seccomp — быстрые win'ы

### F1. Pod Security Admission на namespace

В `bootstrap.sh`, сразу после создания namespace, и в описании staging/prod-namespace (создаются Argo CD через `CreateNamespace=true`, поэтому лейблы нужно проставлять отдельно — Argo CD их не ставит сам):

```bash
kubectl label namespace "$NAMESPACE" \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest \
  --overwrite
```

Для staging/prod добавьте это в `deploy/argocd/app-staging.yaml` / `app-prod.yaml` как отдельный manifest, применяемый до синхронизации приложения, либо проще — заведите `templates/namespace-labels` нельзя (namespace не в ведении чарта), так что сделайте маленький `deploy/k8s/namespaces.yaml`:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: bank-staging
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
---
apiVersion: v1
kind: Namespace
metadata:
  name: bank-prod
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
```

Примените один раз вручную (`kubectl apply -f deploy/k8s/namespaces.yaml`) до первого `Sync` в Argo CD — `restricted` сразу отклонит поды без правильного `securityContext`, так что сначала проверьте, что у **всех** сервисов (не только frontend) выставлены `runAsNonRoot`, `seccompProfile`, `capabilities.drop: [ALL]` — см. F2.

### F2. Базовый securityContext для всех сервисов

В `values.yaml`, верхнеуровнево:

```yaml
global:
  podSecurityContext:
    runAsNonRoot: true
    seccompProfile: { type: RuntimeDefault }
  containerSecurityContext:
    allowPrivilegeEscalation: false
    readOnlyRootFilesystem: true
    capabilities: { drop: ["ALL"] }
```

В `templates/deployment.yaml`:

```yaml
spec:
  template:
    spec:
      securityContext:
        {{- toYaml .Values.global.podSecurityContext | nindent 8 }}

        - name: {{ $name }}

            {{- toYaml .Values.global.containerSecurityContext | nindent 12 }}
```

**ПРОВЕРЬТЕ**: `readOnlyRootFilesystem: true` может сломать Java-сервисы, если они пишут временные файлы (логи, кэш) в `/tmp` без отдельного volume. Добавьте `emptyDir` на `/tmp`:

```yaml
volumes:

  - name: tmp
```

Это нужно добавить в общий (не только frontend) блок volumes/volumeMounts в `deployment.yaml`.

### F3. NetworkPolicy default-deny + явные разрешения

`helm/bank-platform/templates/networkpolicy-default-deny.yaml`:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: {{ include "bank-platform.fullname" . }}-default-deny
  namespace: {{ .Release.Namespace }}
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
  egress:
    # DNS всегда нужен
    - to:
        - namespaceSelector: {}
      ports:
        - { protocol: UDP, port: 53 }
        - { protocol: TCP, port: 53 }
```

`templates/networkpolicy-allow-internal.yaml` — разрешаем сервисам ходить друг к другу и к инфраструктуре внутри namespace (упрощённо, по меткам namespace, а не по точечным selector'ам — **ПРОВЕРЬТЕ**, достаточно ли этого, точечные policy per-service надёжнее, но требуют знания реальных labels Postgres/RabbitMQ/Keycloak, которые я не видел):

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: {{ include "bank-platform.fullname" . }}-allow-intra-namespace
  namespace: {{ .Release.Namespace }}
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: {{ .Release.Namespace }}
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: {{ .Release.Namespace }}
```

`templates/networkpolicy-allow-ingress.yaml` — трафик от ingress-nginx к frontend/gateway:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: {{ include "bank-platform.fullname" . }}-allow-from-ingress
  namespace: {{ .Release.Namespace }}
spec:
  podSelector:
    matchExpressions:
      - { key: app.kubernetes.io/name, operator: In, values: [frontend, gateway-service] }
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: ingress-nginx
```

Это компромиссный, не идеально детализированный набор (идеал — отдельная policy на каждую пару сервис→БД), но закрывает главную дыру из вашего замечания: «любой под в namespace может ходить в Postgres» — после default-deny это уже не так для подов за пределами namespace, а внутри он всё ещё разрешён широко. Точечная сегментация — отдельная задача, требующая знания реальных меток StatefulSet'ов Postgres/RabbitMQ.

## Блок G. nginx — security headers и health endpoint

Замените `frontend/nginx.conf` (из этапа 2.6) на расширенную версию:

```nginx
server {
    listen 8080;
    server_name localhost;
    root /usr/share/nginx/html;
    index index.html;

    server_tokens off;

    add_header X-Content-Type-Options nosniff always;
    add_header X-Frame-Options DENY always;
    add_header Referrer-Policy strict-origin-when-cross-origin always;
    add_header Permissions-Policy "geolocation=(), microphone=(), camera=()" always;
    # ПРОВЕРЬТЕ: connect-src должен включать реальный GATEWAY_URL/KEYCLOAK_URL
    # окружения, иначе CSP заблокирует запросы приложения. Если фронтенд
    # грузит что-то с CDN, добавьте это сюда же.
    add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self' https: wss:; frame-ancestors 'none'" always;

    gzip on;
    gzip_vary on;
    gzip_types text/plain text/css application/json application/javascript text/javascript image/svg+xml;
    gzip_min_length 1024;

    location = /healthz {
        access_log off;
        return 200 "ok\n";
        add_header Content-Type text/plain;
    }

    location = /config.js {
        add_header Cache-Control no-store;
        try_files $uri =404;
    }

    location /assets/ {
        add_header Cache-Control "public, max-age=31536000, immutable";
        try_files $uri =404;
    }

    location / {
        add_header Cache-Control no-cache;
        try_files $uri $uri/ /index.html;
    }
}
```

**ПРОВЕРЬТЕ** `Content-Security-Policy`: если Keycloak-redirect открывается в том же окне (не iframe), `frame-ancestors 'none'` нормален; если у вас где-то используется silent SSO check через iframe, понадобится `frame-ancestors 'self'` вместо `'none'` и отдельный `frame-src`. Также `style-src 'unsafe-inline'` — компромисс ради CSS-in-JS/Vite, в идеале заменить на nonce, но это требует правок в сборке.

Добавьте пробы в `deployment.yaml` для frontend (если их ещё нет):

```yaml
{{- if eq $name "frontend" }}
livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
  initialDelaySeconds: 5
  periodSeconds: 10
readinessProbe:
  httpGet: { path: /healthz, port: 8080 }
  initialDelaySeconds: 3
  periodSeconds: 5
{{- end }}
```

```yaml

apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: bank-app-secrets

  refreshInterval: 1h

      remoteRef: { key: bank/staging/bill-db-password }
    - secretKey: DEPOSIT_DB_PASSWORD
      remoteRef: { key: bank/staging/deposit-db-password }
    - secretKey: NOTIFICATION_DB_PASSWORD
      remoteRef: { key: bank/staging/notification-db-password }
    - secretKey: RABBITMQ_USERNAME
      remoteRef: { key: bank/staging/rabbitmq-username }
    - secretKey: RABBITMQ_PASSWORD
      remoteRef: { key: bank/staging/rabbitmq-password }
    - secretKey: MAIL_USERNAME
      remoteRef: { key: bank/staging/mail-username }
    - secretKey: MAIL_PASSWORD
      remoteRef: { key: bank/staging/mail-password }
```

Аналогично для `bank-prod` (другой `namespace`, другие пути `bank/prod/...`) и для `*-db-credentials` (`kubernetes.io/basic-auth` secrets с `cnpg.io/reload=true` — добавьте `target.template.metadata.labels`, чтобы лейбл проставился после синка ESO):

```yaml

    name: account-db-credentials

    template:
      metadata:
        labels:

```

Это закрывает главный риск из вашего пункта 13 — пароли больше не проходят ни через `.env`, ни через историю терминала для staging/prod; секреты хранятся в облачном secret-manager и попадают в кластер только через ESO с ограниченным IAM-доступом сервис-аккаунта.
